# CUDA-MCGS PTX Extension Composition Findings

**Status:** Bounded discovery disposition

“Can” records an observed mechanism or workaround. “Should” is the durable design disposition after ownership, correctness, compatibility, diagnostics, hot-path cost, and lifecycle are considered.

## CUDA-MCGS ownership lane

| ID | Evidence | What can work | What should be durable | Disposition |
|---|---|---|---|---|
| MCGS-EXT-001 | Strict fixture manifests and deterministic ordering rejected incompatible plans before native work; one- and two-fragment launches matched the oracle. | The prototype's small JSON records and JavaScript validator work for discovery. | CUDA-MCGS must own the normative Extension Surface/Point/Fragment schemas, point semantics, least-authority context, resource plan, deterministic ordering, ABI mapping, and conformance. | Use the findings to finish the specification; do not promote prototype schemas verbatim. |
| MCGS-GEN-001 | Hand-authored PTX linked and executed, while CUDA-source fragments could not be made linkable through current CUDA-JS compilation. | Continue using hand-authored PTX as a narrow reproducer. | Production CUDA-MCGS should have an owned generator/lowering boundary that emits or requests validated relocatable PTX and records exact provenance/options; handwritten PTX must not become the authoring model. | Retain only as disposable evidence; specify generator inputs/outputs after CJS-PTX-001 is resolved. |
| MCGS-COST-001 | Two linked fragments produced two SASS calls, a 7,016-byte cubin, and 31 kernel registers; fused source produced zero calls, 4,520 bytes, and 17 registers. | Direct PTX calls are correct and avoid generic function-pointer dispatch. | “No generic dispatch” must not be rewritten as “zero bound cost.” Extension points must be sufficiently coarse or cold, and promotion needs representative emitted-code/resource/performance thresholds against fused controls. Tiny hot hooks may need fused generation instead of separate PTX. | Constrain the PTX profile in the specification and run a controlled representative follow-up before production selection. |
| MCGS-UNBOUND-001 | No-point and unbound core PTX and final cubin were byte-identical; both contained zero extension calls/symbols. | Generation can omit unbound points completely. | Preserve exact unbound disappearance as a CUDA-MCGS composer/conformance requirement. | Promote the invariant and metamorphic test, not the experiment implementation. |
| MCGS-VALID-001 | The portable checker found profile/digest/export fixture inconsistencies but native linking was still required to prove PTX validity. | Regex checks are useful for fast fixture failures. | Do not build a home-grown PTX parser. Validate authoritative manifest fields and exact bytes, then let CUDA-JS/nvJitLink own generic PTX/link validity; inspect the final cubin/SASS for CUDA-MCGS acceptance. | Keep the checker explicitly non-authoritative. |
| MCGS-SEARCH-001 | One launch performed a tiny finite transition/transposition/cycle/evaluate/backup loop with no host intermediate. | A single-thread synthetic search is enough to test composition lifecycle. | Scheduler, concurrency, evaluator residency, representative graph behavior, and resource topology remain separate evidence gates. | Do not use this result to select SCHED-001 or claim production search readiness. |
| MCGS-PAIR-001 | An exact clean sibling checkout could be packed and installed reproducibly; generated install state was removed. | Local exact-revision packaging is practical for discovery. | Released work should consume a versioned CUDA-JS artifact and record an exact CUDA-MCGS/CUDA-JS compatible-pair manifest; no sibling checkout or private import should be required. | Add to the minimum Search Image/package contract and later release conformance. |

## Decision summary

The selected PTX direction remains viable for correctness and static direct binding, but its durable form is not “hand-write PTX and accept every direct call.” CUDA-MCGS should retain unbound disappearance, deterministic pre-ignition composition, and final-binary evidence as hard requirements. It should constrain extension granularity until representative evidence shows acceptable bound cost. CUDA-JS should add only the concrete consumer-neutral compile capability demonstrated missing here: relocatable device code. Linux remains an explicit two-owner sequence rather than a Windows workaround disguised as portability.

CUDA-MCGS follow-up is tracked in [UMCGS #30](https://github.com/iteathen/UMCGS/issues/30).
