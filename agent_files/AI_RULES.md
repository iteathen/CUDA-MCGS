# AI Rules

**Scope:** Hard rules for automated agents. These rules are concise by design; linked files contain the method.

1. Read root `AGENTS.md` before any change.
2. Follow authority order; report material contradictions.
3. Do not edit a critical boundary without a completed critical assessment, adequate reasoning, authority, and evidence.
4. Work by ownership boundary, not arbitrary file count.
5. Do not turn the first plausible idea into an implementation plan for substantial or critical work; complete the proportional assessment first.
6. Answer every applicable assessment question through a strong proposer/adversary/defender/integration pass; do not use a straw-man critic.
7. Do not defend an original proposal after evidence exposes a better boundary, narrower scope, experiment, or rejection.
8. Do not call a design simple when it omits sound fundamentals or exports complexity to callers, memory, synchronization, migration, recovery, cleanup, diagnostics, tests, or future integrations.
9. Keep assessment and planning administration proportional: one authoritative record by default, links instead of duplication, and no manual ledger without a real consumer and owner.
10. Treat a plan as a hypothesis beneath current authority, not as authority or permission to ignore newly triggered doctrine.
11. Execute only a current node that is explicitly ready, dependency-complete, correctly owned, and supported by current authority, repository state, environment, and runnable evidence.
12. Before a material operation, state expected local and wider effects, acceptance, the cheapest decisive falsifier, rollback/safe stop, cleanup obligations, and conditions requiring plan revision.
13. Apply one coherent ownership-sized operation at a time; do not equate an operation with one file or combine unrelated plan nodes.
14. Inspect exact actual effects immediately after each material operation and compare them with expected effects before continuing.
15. Run the focused falsifier, register created/modified/obsolete state, reconcile affected contracts/callers/resources/lifecycle/design/cleanup, and classify the outcome as continue, accept, pause, revise, rollback, fail, or supersede.
16. Treat changes to cause, owner, authority, public contract, schema, ABI, consequence horizon, resource model, risk, acceptance, rollback, output, downstream order, or cleanup disposition as material deviations requiring plan revision.
17. Do not mark a node accepted while invalid partial state, competing authority, stale generated forms, abandoned resources, unresolved contradictions, unowned residue, or false downstream preconditions remain.
18. Keep execution administration proportional: use one plan-execution record only when coordination, continuation, invalid intermediate states, high consequence, or another evidence consumer requires it; do not duplicate issue, plan, execution, cleanup, PR, and handoff histories.
19. Every material task-created, temporarily modified, superseded, partial, generated, diagnostic, local, remote, external, sensitive, and coordination item must receive an explicit owner, disposition, and verification.
20. Cleanup means disposition—not automatic deletion. Use remove, restore, retain authority/evidence/recovery, archive, quarantine, transfer, supersede, retain temporarily with an objective trigger, or protect unchanged.
21. Do not destroy user/pre-existing uncommitted work, shared active resources, project authority, evidence/provenance/security state, rollback/recovery checkpoints, externally owned state, protected/default/shared branches, or items with active dependents without exact authority.
22. Before destructive cleanup, verify exact target identity, owner, working directory/selector, dependents, authority, evidence/rollback needs, expected effect, and decisive verification; use the narrowest selector and preview when available.
23. Do not use broad recursive deletion, `git clean -fdx`, `git reset --hard`, stash destruction, force-push, shared/protected branch deletion, PR/issue closure, review resolution, release/package deletion, or remote resource removal for cosmetic cleanliness.
24. Do not delete historically useful stale material silently; archive it with date, location, reason, successor, and removal context.
25. Do not treat a successful command, clean diff, exited process, or merged PR as cleanup proof when state is remote, asynchronous, shared, sensitive, generated, cached, or eventually consistent.
26. Reconcile local files/folders, tracked files, generated/build output, branches/worktrees/stashes, remote refs, PRs/issues/reviews/claims, processes/ports/containers/locks, GPU/device state, credentials/permissions, backups/persistence, artifacts/releases/packages, and external resources when triggered.
27. Delete task-owned local and remote branches/worktrees only after merge/closure/supersession/abandonment and after stacked/dependent PR, recovery, audit, release, automation, and user needs are resolved.
28. Preserve PR and issue history; make current state truthful. Do not close issues merely because a PR merged or resolve blocking reviews without evidence.
29. If a secret may have been exposed, deletion is insufficient: revoke or rotate it, preserve bounded incident evidence, and inspect downstream copies according to security policy.
30. Cleanup debt is permitted only when immediate cleanup is less safe than retained state; it must be exact, contained, owned, non-accidental, protected from ordinary use, objectively triggered, independently actionable, and explicit about parent acceptance.
31. Do not use cleanup debt to hide ordinary incomplete work, an unmet acceptance criterion, unsafe residue, or unrelated repository mess.
32. Keep cleanup administration proportional: routine scratch and ordinary branch cleanup are handled inline; use a durable cleanup record only for shared, external, sensitive, retained, recovery-critical, long-lived, atomic, or independently blocked state.
33. Before a sanity check, freeze the exact revision or artifact and declare `full`, `bounded`, or `sampled`.
34. Build a complete semantic coverage map and split it into review branches small enough for one focused session and full attention to every material semantic unit.
35. Treat a review branch as a semantic coverage packet, not automatically a Git branch; do not split solely by file or line count.
36. Split a branch when it has multiple primary owners, mixes unrelated contracts or paths, requires sampling or skimming, prevents localization of findings, or exceeds active context for both mechanism and consequence.
37. Do not call sampled or silently incomplete coverage a full or system-wide sanity check.
38. In a full sanity check, account for every declared surface at risk-justified depth; do not require uniform exhaustive depth for unrelated low-risk units.
39. Interrogate every material semantic unit through purpose/specification, owner/LEGO boundary, inputs/outputs/effects, callers/dependencies, state/identity/lifetime, foundational contracts/ranges, design-principle alignment, ordering/resources/pressure, failure/cleanup, counterexamples, decisive evidence, and wider consequences.
40. Apply every objectively triggered specialist module, including design/universality, graph/search, evaluator/numerics, GPU/concurrency, finite memory, persistence/compatibility, security/native execution, performance, generated/JIT/ABI, external resources, destructive behavior, cleanup, and diagnostics.
41. Treat tests, compilers, linters, analyzers, sanitizers, profilers, and benchmarks as evidence—not substitutes for semantic, specification, design, integration, and cleanup reasoning.
42. Do not infer system coherence from passing leaf branches; reconcile producer/consumer boundaries, end-to-end paths, cross-cutting concerns, lifecycle, cleanup, contradictions, and findings.
43. Do not quietly repair findings inside an independent sanity check or audit; authorize remediation separately and revalidate affected branches, boundaries, paths, and cleanup state.
44. Keep sanity administration proportional: one canonical record only when needed, grouped low-risk coverage only when branch sizing remains valid, no form per file/function, and no duplicate findings ledger.
45. Before PR review, record the PR, intended target, exact head SHA, relevant base/merge base, comparison range, review mode, cleanup state, and claim limits.
46. Review the actual complete diff, ancestry, affected context, current discussion, plan-execution fidelity, cleanup/disposition, and current-head evidence; do not treat the PR description or green CI as proof.
47. Every material PR receives complete author-side review; label it non-independent unless a genuinely independent reviewer performed the review.
48. Require independent review when project phase, repository protection/CODEOWNERS, owner instruction, or objective consequence triggers it.
49. Classify review comments as blocking defect, question/potential blocker, cleanup debt, non-blocking improvement, or informational; do not block on unrelated cleanup or personal preference.
50. A head change invalidates affected approval/authorization. A material base change invalidates affected integration and cleanup evidence.
51. Do not approve or merge while required checks are pending/failed, blocking findings/threads remain, material cleanup is unsafe/unowned, or mergeability/target/closure is unknown.
52. Do not resolve another reviewer's blocking thread without evidence and appropriate reviewer/owner disposition.
53. Merge only the exact accepted head, with an expected-head guard where supported, after revalidating checks, reviews, protections, discussion, target, ancestry, issue closure, branch/worktree effects, cleanup, and conflicting work.
54. Choose squash, rebase, or merge commit deliberately; squash is the pre-release default for one coherent result.
55. Do not bypass branch protection, CODEOWNERS, required checks, or a merge queue; do not force-update the target to finish.
56. Do not claim merge completion until the target/resulting SHA, intended tree, issue closure, local/remote source branches/worktrees, dependent work, temporary permissions, artifacts, and external resources are verified or safely tracked.
57. An exact-head single-maintainer authorization is not independent approval and cannot waive substantive gates or cleanup safeguards.
58. Always organize the repository as though it is already a very large project; current small size is not permission for flat or temporary structure.
59. Decide product area, component, lifecycle owner, dependency direction, public surface, and eventual disposition before creating production artifacts.
60. Do not add source code to the repository root or create unowned catch-all `utils`, `common`, `shared`, `misc`, `helpers`, or equivalent dumping grounds.
61. Do not create a component without its manifest, README, registry entry, public/internal boundary, validation ownership, and lifecycle/disposition.
62. Do not deep-import another component's internal files; depend only through its declared public contract.
63. Do not create circular component dependencies.
64. Do not split a repository, service, or package merely because file count is growing; require an independent lifecycle, release, security, ownership, or consumer boundary.
65. Do not make speculative fixes. Reproduce, observe, classify, repair, retest.
66. Do not weaken tests, gates, thresholds, assertions, cleanup safeguards, or safety checks to make work pass.
67. Do not claim success without running the relevant validation and cleanup verification.
68. Do not claim publication until the remote state is verified.
69. Do not introduce hidden CPU participation into GPU-resident search.
70. Do not introduce hidden domain, evaluator, graph, value, action-space, or memory assumptions into the universal core.
71. Do not encode accidental first-case limits in foundational schemas or types.
72. Do not add general-purpose device allocation to the active hot path without an accepted memory/lifetime design.
73. Do not copy or adapt third-party implementation without exact revision, license, explicit reuse decision, and donor-artifact disposition.
74. Do not expose secrets, arbitrary native capabilities, unchecked executable schemas, or unsafe pointer capabilities.
75. Do not leave stale authority, plan state, cleanup state, indexes, component manifests, registry entries, findings, invalidated execution/review evidence, execution-created or review-created state, review threads, PR state, remote branches, credentials, artifacts, external resources, or handoff state after a change.
76. Record genuine blockers and the next coherent action in `next_step.yaml` or a cleanup-debt issue as appropriate.
77. Prefer a complete coherent result over many tiny context-reloading cycles.
78. When a task exceeds one focused session, spans multiple semantic owners/contracts/paths, contains independent unknowns, crosses agents/sessions, or would force sampling or skimming, create a focus-branch map before deep execution.
79. Treat a focus branch as a semantic work packet, not automatically a Git branch, issue, PR, component, directory, or document.
80. Keep one canonical parent task and integration spine owning the global outcome, authority, invariants, vocabulary, dependency graph, invalidation, contradictions, cleanup, and closure.
81. Size each leaf focus branch so one qualified agent can retain its owner, mechanism, dependencies, failure/resource/cleanup behavior, evidence, consequence horizon, and integration obligation without sampling or skimming.
82. Split focus branches by semantic ownership, independent output, validation, rollback, cleanup, and consequence—not equal file count, line count, token count, or agent count.
83. Every material focus branch must state stable ID, parent-plan version, owner, exact inputs/revisions, scope/non-goals, write permissions, preserved global invariants, output contract, acceptance/falsifier, invalidation, cleanup, and integration obligations.
84. Normally own only one active focus branch at a time; checkpoint exact revision, partial state, evidence, cleanup, and next action before switching.
85. Do not let a focus branch silently redefine parent-level terminology, ownership, schema meaning, ABI, identity, units, ranges, resource budgets, compatibility promises, or acceptance criteria; route shared changes through the integration spine and invalidate dependents explicitly.
86. Parallelize focus branches only when owners and write surfaces do not overlap, shared contracts are frozen or coordinated, dependencies are acyclic, acceptance/rollback/cleanup are independent, and one integration owner reconciles all outputs.
87. Do not treat locally accepted focus branches as proof of parent completion; centrally reconcile exact outputs, contradictions, boundaries, end-to-end behavior, lifecycle, resources, compatibility, security, performance, and cleanup against one final revision.
88. Create separate Git branches, issues, PRs, worktrees, or documents for focus branches only when isolation, owner, deliverable, risk, dependency, review, transport, rollback, or closure is independently meaningful.
89. Rebranch when evidence reveals the task’s true shape; preserve prior branch IDs and dispositions, version changed dependencies/outputs, and invalidate affected work rather than silently rewriting the map.
