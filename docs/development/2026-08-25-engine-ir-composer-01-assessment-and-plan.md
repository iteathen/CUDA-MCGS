## Critical assessment

### Representation boundary

A single 989-requirement object schema would centralize other owners' facts and make optional deletion, review and evolution unsafe. A generic descriptor DSL would merely move the problem into a runtime-like schema interpreter and erase domain-specific validity. Digest-only references would preserve names but could not reject invalid fields, ranges, permissions or cross-owner bindings.

The smallest sufficient total system is therefore:

1. a proposal-version Search IR contract set and requirement-coverage index;
2. shared closed structural primitives for IDs, versions, quantities, schemas, ports, identities and owner references;
3. one strict normalized fragment per semantic owner, with optional owners represented by structural omission;
4. one thin framework envelope that selects exact owner contract/profile identities and public bindings;
5. one deterministic reference Composer that validates cross-owner closure and derives resource, progress, layout, output/session/extension, deletion and cleanup plans;
6. canonical restricted Device-JS/Search Program source plus a public CUDA-JS request/package projection; and
7. evidence manifests for coverage, identity, rejection, deletion, rollback and provenance.

The proposal representation is a new version family rather than an edit to `cuda-mcgs.search-ir/0.1.0`. The first evidence version is `cuda-mcgs.search-ir/0.2.0`; its proposal status comes from its governing specifications and does not imply acceptance. Version 0.1.0 remains byte-for-byte authoritative for its accepted boundary.

### Organizational disposition

This node is explicitly bounded, non-production evidence. New machine-readable contract artifacts belong under `schemas/search-ir/0.2.0/`; the reference normalizer/Composer, fixtures and evidence capsule belong under a dedicated `experiments/search-ir-composer-reference/` experiment. No `components/` production owner is created yet. A production component manifest, package and API are justified only after integrated semantic acceptance establishes an independently owned lifecycle and public boundary.

The reference Composer is ordinary Node.js. Generated device-program inputs are restricted Device-JS source text and versioned metadata only. No C/C++, CUDA C++, native addon, direct FFI/Driver use, hand-written PTX, embedded CUDA source, CUDA-private handle, ABI layout or native subprocess belongs in this node.

### Identity, ordering and deletion

Every meaning-affecting selected contract/profile, normalized field, explicit semantic order, owner binding, source byte, generator version, resource/progress/output/session/extension plan and public CUDA-JS requirement participates in its owning identity layer. Meaning-insensitive maps and sets use raw JavaScript/Unicode code-unit ordering; meaning-sensitive arrays retain declared order. Canonical bytes and digests cannot depend on locale, insertion order, filesystem discovery, host platform or CUDA-JS-private output.

Optional evaluator, live observation, Search Session, extension substrate, channel, capability and product inputs are omitted when absent. Omission must remove every solely owned schema field, port, source region, layout, resource, work class, synchronization/public capability requirement, diagnostic and teardown item. A disabled placeholder, empty runtime object, no-op callback or dormant branch fails deletion. Truthful selection/provenance identity differences are compared separately from residue-bearing derived outputs.

### Requirement traceability and evidence split

Every proposal requirement ID will have exactly one primary owner and one evidence disposition:

- structural schema;
- semantic/cross-owner normalizer;
- deterministic composition/package projection;
- IR identity/deletion/rejection case;
- deferred `ENGINE-REFERENCE-01` semantic oracle;
- explicit cross-specification proof; or
- later native/compatible-pair qualification.

The coverage index links IDs to evidence without copying normative sentences. A requirement can have secondary evidence, but it cannot disappear, be counted twice as two owners, or be reported complete when its disposition is a later gate. This node proves representation and composition only; `ENGINE-REFERENCE-01` owns materially different behavioral models, and `ENGINE-CONTRACT-ACCEPTANCE-01` reconciles both on one exact revision.

### CUDA-JS completeness classification

No additional generic CUDA-JS feature is required for backend-neutral schema, normalization, composition or CUDA-free reference evidence. Current public Device-JS contracts naturally carry restricted source and consumer-neutral compiler/resource/operation requirements. The previously classified CUDA-JS issue #123 gap is resolved by the public device-scope release/acquire Device-JS contract in `cuda-js@0.1.0-alpha.7`. A selected Channel profile names that public capability without making it universal; native Channel execution still requires the later exact compatible-pair qualification rather than a stale missing-capability label.

Any later urge to add native code, CUDA spelling, private artifact inspection or an awkward synchronization recipe in CUDA-MCGS is a stop signal. The need must be reclassified as either existing public CUDA-JS capability, a new consumer-neutral CUDA-JS contract, or evidence that the CUDA-MCGS design is wrong.

### Strongest challenges

The strongest simplification is to keep only hashes of opaque owner profiles. It fails because invalid ranges, missing lifecycle/failure meaning and permission/resource conflicts would survive until lowering. The strongest overengineering risk is a universal schema language and general workflow compiler. It is rejected: schemas are finite closed data, owner validators are static JavaScript, and the generated program contains no runtime registry/interpreter/late binding. The strongest underengineering risk is claiming coverage from schema parseability alone. It is rejected: cross-field ownership, conservation, closure, deletion and identity require executable reference falsifiers.

### Assessment disposition

Proceed sequentially through owner-sized focus branches. Shared vocabulary and identity changes route through the integration spine and invalidate every affected downstream leaf. No owner schema leaf may invent semantics missing from its proposal; it must stop and return the gap to the owning specification. No production lowering starts from proposal 0.2.0 evidence.

## Token and attention posture

This is critical cross-owner work. One semantic leaf is active at a time and must retain reserve for negative fixtures, exact-effect inspection, integration, cleanup and honest claim limits. Raw requirement inventories and canonical fixtures are generated/read once and reused by exact digest. Optional prose polish, native execution, product fixtures, performance work and production packaging defer first. A new owner, vocabulary rewrite, repeated repair without causal evidence, requirement-count drift, identity collision, native temptation or inability to fit an owner leaf with its falsifiers triggers replan or a smaller split.
